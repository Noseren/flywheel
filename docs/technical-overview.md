# Flywheel 如何工作

Flywheel 想解决的是一个具体问题：**让 Agent 可以反复尝试改进，同时让人知道改了什么、有没有变好，以及为什么停下来。**

安装和演示项目见 [README](../README.md)。下面从一次代码修复开始解释，再介绍实现中的几个名字。

## 一次任务会发生什么

假设你希望修复库存预留：重复商品要合并计算，库存不足时不能扣掉一半。

Flywheel 先与你确认目标、允许修改的文件，以及如何检查结果。随后实际运行原始代码，记录哪些检查通过、哪些失败。这份修改前的结果叫作**基线（baseline）**，用于后续比较；基线失败是正常起点，检查根本无法运行则是另一个需要处理的问题。

接着，Agent 在独立副本中修改代码。这个尚未被接受的版本叫作**候选（candidate）**。Flywheel 用约定的检查验证它：如果符合保留条件，就让它成为新的正式版本；否则留下失败证据，继续尝试或暂停。

```text
确认目标和检查方式
        ↓
运行原始版本，记录基线
        ↓
Agent 修改一个候选副本
        ↓
按固定标准验证
        ↓
保留或拒绝 → 继续尝试 / 暂停
```

将候选变成正式版本，在代码里称为**晋升（promote）**。晋升前，系统核对实际评价、修改范围和版本是否匹配。

## 为什么要固定评价标准

固定标准让修改前后的结果可以比较。Flywheel 在准备阶段确定目标、修改边界和检查方式，然后保存它们的内容标识。这个动作叫作**冻结**。用于检查结果的测试或评分程序叫作**评价器（evaluator）**。

发现评价器遗漏要求或错误拒绝合理实现时，应暂停任务，确认修订后的评价方式，并重新建立基线。

这里要分清三个结论：

| 结论 | 回答的问题 |
| --- | --- |
| 检查执行完成 | 是否真正运行了检查并取得证据？ |
| 候选值得保留 | 这次修改是否满足约定的保留标准？ |
| 目标已经达成 | 证据是否足以证明用户的完整要求得到满足？ |

例如，修好了重复商品问题，但库存不足时仍会部分扣减：这个版本可能值得保留，却还没有完成目标。

冻结评价器负责比较候选；独立目标判定再对照原始要求、正式版本和评价证据，确认能否报告完成。两者都依赖证据质量，仍可能遗漏或误判。

## 谁负责什么

用户通常只需要与任务对话。内部则把职责分开，避免所有决定都交给一个 Agent。

| 代码中的名字 | 可以怎样理解 | 负责什么 |
| --- | --- | --- |
| **Session** | 一次任务的运行与恢复入口 | 接收命令，执行步骤，处理暂停和继续。 |
| **Capability** | 一类工作的职责与权限边界 | 例如准备项目（Init）或优化项目（Run），声明可以使用哪些服务。 |
| **Policy** | 系统执行的流程规则 | 规定何时准备、验证、保留或暂停，由可信代码实现。 |
| **Service** | 具体工具能力 | 调用模型、执行程序、读写文件、管理版本等。 |
| **Manager** | 任务的沟通窗口 | 解释问题、接收干预、提出建议。 |

核心关系是：**Session 按 Policy 运行任务，Agent 和工具完成具体工作，系统校验结果。**

终端和桌面界面通过同一套命令与事件操作任务。

## 什么时候需要多个 Agent

当前默认让一个 Agent 完成准备或优化。遇到具体疑点或可以独立分工的工作时，它可以请求帮助：

- **work**：分工处理独立部分，例如分别调查库存和金额模块。
- **check**：请另一个 Agent 检查明确问题，例如某条测试是否错误地排除了合理实现。

被派出的 Agent 在记录中叫作 **Child Job（子任务）**。它提交报告或产物，由原 Agent 核对、整合，再交给统一评价。

协作有明确限制：当前最多一层，work 每批最多两个子任务、check 一个；全任务最多两批。每批连同原 Agent 的续接最多120秒，并受共享预算约束。

另外两种名字出现在评价配置中：**Tasking** 是按要求运行被测对象、取得输出，**Judge** 是对无法仅靠程序检查的质量做独立模型评价。例如优化客服 Prompt，先生成回复，再检查语义质量。系统会为必要评价预留预算。

## 失败和中断之后

正式版本、候选、评价证据和用量都保存在项目记录中。恢复时，系统核对这些记录，复用仍有效的完成结果，并接续原来的预算账本。

候选被拒绝也消耗尝试次数；模型用量暂未返回时保留预估占用。时间或 token 预算不足会暂停。

这些约束主要依靠独立工作目录、文件内容校验和持久记录实现。执行环境使用主机权限，建议在有备份的副本中运行，每个项目使用一个控制进程。

## 当前流程与旧流程

代码中有两个名称：

- **compact**：新任务的默认流程，即本文介绍的精简闭环和有界协作。
- **legacy**：保留的旧流程，通过 `--legacy-workflow` 显式使用，包含更多独立规划、审查、选择和目标判定步骤。

已有任务按原流程恢复，新任务默认使用 compact。

**Target Assess** 是独立目标判定：对照原始目标、正式版本代码与评价证据，返回达成、未达成或证据不足。它与决定是否保留某个候选是两件事。`preview.2` 的新 compact 任务已包含此步骤，旧任务沿原流程恢复。

## 按需组件路由

基础闭环保留，把额外能力整理为组件，由独立的**路由 Agent**在准备和优化的关键节点判断需要哪一种帮助。例如：

| 发现的问题 | 可以选择的能力 |
| --- | --- |
| 目标有多个容易遗漏的要求 | 需求分解、评价覆盖审查 |
| 失败原因不清楚 | 定向诊断或 check |
| 存在几种值得尝试的实现方向 | 多候选搜索、独立比较 |
| 准备报告任务完成 | 独立目标判定 |
| 原评价方式已经不能忠实表达目标 | 受控修订评价，重新建立基线 |

路由负责提出选择，系统控制权限、预算和执行。组合多个候选后，会对组合结果重新验证。

完成条件是：**宣布整体目标达成前，必须有独立目标判定。** 如果预算耗尽而来不及判定，就报告暂停和证据不足。

`preview.2` 已接入组件路由。真实复杂项目实验用到了评价计划、提案和 check 协作，其他高级组件的实际效果仍待验证。可选建议超时且用量已确认时，会记录未采纳并继续基础流程；未知调用保留现场等待恢复。

判定为证据不足时暂停；判定未达成时，在授权和预算允许范围内继续调查。用户会看到当前版本、判定摘要、具体未决事项和完整报告入口。缺少覆盖与已证实失败分别说明；摘要只给用户，私有判定理由不进入路由或优化上下文。旧记录没有摘要时展示已有理由，并保留完整报告。

独立判定也可能过于保守，从而增加消耗。当前按版本和证据复用判定，保留默认预算限制；证据不足后自动补齐验证并收敛的路径仍不完整。本版定位为源码预览。

评价规则需要变化时，目前会暂停并提示重新准备。自动验证和激活新规则、调整核心流程仍是后续工作。
