把完整初始化建议写入 {{document_path}}，使用简体中文自然语言。至少清楚说明：

- 优化对象及为什么选择它；
- 如何执行并收集输出；
- 长期优化目标；
- 如何评价、使用哪些证据以及什么情况下评价不完整；
- 评价拓扑及依据：自然样本分布使用 train/holdout，有限公开规格或整体检查使用无分区 candidate；若拆分，说明语义隔离且不得让 holdout 独占公开要求；
- 用户明确提出的红线；没有明确红线时必须写明不新增红线；
- 允许修改和禁止修改的范围；
- evaluator/scorer 的实现与 smoke 方法。

方案必须忠实保留用户原始目标中的显式要求。凡目标中出现类名、函数名、字段名、路径、数据结构或精确输出格式，都要原样写入对应目标和验收说明；不能用更泛化的描述代替，也不能擅自改成项目里看起来相近的名称。

Init Smoke 只能规划一个有界代表单元：sample 模式取 train 第一个逻辑位置，candidate 模式取两个 Guide 共同指定的最小公开检查。它只验证最小执行与评价链路；不得把多条正反例、完整 train/holdout、全量测试或 evaluator 自检序列写成 Smoke 步骤。其他 scorer 正反自检或正常命令可单独说明为 Contract 可行性检查或正常 Run 评价，但不属于 Init Smoke。
Smoke 不要求当前 baseline 通过目标功能断言；代表单元因待优化功能未实现而确定性失败，只要真实调用完成、评价器正确记录失败且报告可信，仍是有效低分基线。只有协议、工具、依赖或报告链路失败才表示 Smoke 本身不成立。

不增加机器业务字段；rubric、权重、样本格式和 scorer 约定都保留在这份 Agent 可读文档中。

如果采用 rubric 评价，必须为每个维度分别写出评价对象、证据要求、每一个可取分值的独立评分细则、权重或聚合方法，以及硬性失败和评价不完整的条件。不得只给所有维度共用一套“差/一般/好”或“0/1/2”泛化定义。还要明确区分：可执行 evaluator 只负责具有无歧义真值的 schema、精确匹配、结构化集合关系、reference accuracy 等确定性计算；Evaluate Agent 负责所有基于完整输入和输出的语义判断。不得建议用关键词、正则、模糊匹配或启发式规则代码化自由文本的事实、政策、承诺、风险或表达质量，也不要把确定性检查器称为完整 rubric evaluator。

仅向 {{destination}} 写以下最小 JSON 引用：

```json
{
  "artifactPath": "项目内待优化对象的相对路径",
  "documentPath": "{{document_path}}",
  "userFacingSummary": "目标：一句话说明希望实现什么。\n评价：一句话说明如何检查实际结果。"
}
```

userFacingSummary 是面向用户的简短确认文案（建议 80–250 字，最多 1200 字），仅包含目标、评价方式；修改授权需要明确时补一行范围。不要写 operation、Capability、manifest、hash、数据路径、合同字段、完整方案或系统说明。它不是技术合同；完整的证据、隔离与执行细节仍保留在 documentPath。用户确认此摘要后由 Runtime 自动完成安全准备与最小试运行。后续修订也必须同步更新摘要，使其忠实对应完整方案。

不要写入其他机器业务字段。
